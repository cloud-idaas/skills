# 角色发现契约与验收

用于 `onboard`、`show roles` 的配套版本核验、结果解释与验收。实际请求和分页由 `alibaba-cloud-idaas` Broker 实现，Skill 只编排命令。

## 固定请求契约

- 支持本次改造的配套 Broker 调用 `ListAssumableCloudAccountRoles` 时始终设置 `includePermissionTemplateRoles=true`，覆盖首次、续页、刷新角色及失败后的重新发现。不暴露用户可选开关，不从用户输入或 profile 配置覆盖成 false。旧版能力不足按下方分级处理，不通过增加用户开关或显式切换 false 绕过。
- Skill 不给 `onboard`、`show roles` 臆造 `--include-permission-template-roles` 参数，也不读取登录缓存绕过 Broker 自行请求 API。
- 服务端 API 的缺省值仍是 false，以兼容其他既有调用方；本 Skill 使用的 Broker 采用固定 true，与 API 默认值是两层约定。
- 当前设备码登录流程发现 USER 主体可用的直接授权角色与权限模板角色。模板须已授权、ENABLED、用途匹配且关联角色有效；本次不新增机器身份登录流程。Broker 的其他应用主体发现入口如复用该 API，也须遵守固定 true 和分页契约。

## 配套版本核验

使用配套发布说明中明确声明支持该契约的 Broker 版本，或维护方核验过的源码构建版本。证据应涵盖 `onboard` 与 `show roles` 共用/各自的 API 请求构造和分页实现。仅检查版本号、命令存在、已安装最新版或出现一个模板角色，都不能证明所有页均固定传 true。

当前本仓库不包含 Broker 实现，也未登记经过验收的最低 Broker release。维护者应在 Broker 发版验收后，将最低版本及对应发布说明链接补入本节；不得猜测版本号或声称旧版已支持。使用时按目标分级：

开发中的配套实现版本为 `0.2.4-beta`；这不是已发布最低版本声明。经维护方提供、确认来源的源码构建可用于联调，正式接入仍须核对对应 release notes。

1. **常规接入或查询角色**：已有可运行 Broker 时照常执行，能力无法确认则如实提示“模板角色发现能力未确认，结果可能不含模板角色”；已知旧版则说明其仅保留改造前的角色发现行为。角色发现和配置生成仍按该版本实际输出处理，不宣称已覆盖模板角色；不因为缺少模板能力证明而阻断存量用户。
2. **以模板角色为验收目标**：若版本已知不支持或配套能力无法确认，暂停模板角色专项验证，提示升级至维护方确认的配套版本。不能用旧版空列表推断没有模板授权，也不能把常规接入成功当作模板专项验收通过。
3. **登录刷新、登出**：始终不受模板角色发现能力检查影响，沿用原流程。

启用新版 Broker 的模板角色发现能力前，应完成 CMDB、PS、RS 配套服务的全量发布及对外 API 元数据更新。CMDB/PS 可在二方库就绪后并行发布，两者全量完成后再发布 RS、启用新版 Broker；不能因二方库已发布就认定旧服务实例会返回新字段。此发布约束不阻断旧版 Broker 的常规接入。

## 分页与结果解释

- Broker 保持实例、主体及固定 true 不变，逐页传递服务端返回的 `NextToken`，直至 token 为空。所有页成功之前，不展示“完整发现”或按部分角色生成最终配置。
- 合并集由服务端按角色 ID 去重、排序并统一分页。Broker 不自行把模板角色再追加一次，不用 ARN 或角色名称替代角色 ID 去重；既有 profile 命名方式保持不变。
- true/false 模式 token 不混用；服务升级或回滚导致 token 不兼容时，从第一页重新发现。分页不是快照隔离，翻页期间新增且排序落在游标之前的授权可能要下一轮刷新才能出现。
- `createdByPermissionTemplate` 表示角色自身是否由模板创建，与当前通过直接授权还是模板授权发现无关。true/false/null（未知）原义保留；不可用它筛选“已授权”角色或伪造缺失值。
- 模板详情条数超过 100，或合并去重原始角色 ID 数超过 500（含失效角色），服务端会拒绝查询；这是保护阈值，不是客户端截断数。不得截断后声称发现成功，也不切换 false 重试。

## 配套验收

在获授权的测试环境使用配套 Broker 验证，不读取或输出凭证。请求取证只保留非敏感参数和页数，不记录 Authorization、Cookie、token 或 STS。

| 场景 | 通过标准 |
|---|---|
| 仅直接授权 | `show roles` 和 `onboard` 均能发现并生成对应 profile，原有角色命名/默认选择逻辑可用。 |
| 仅权限模板授权 | 在模板 ENABLED、USER 用途和关联角色有效时，两条命令均发现角色，无需另补直接授权。 |
| 两路重叠、结果跨多页 | 角色 ID 不重复，后续页角色不遗漏；请求构造或脱敏取证确认每页固定 true。只查看首屏不算通过。 |
| 禁用模板或用途不匹配 | 该模板不会额外贡献角色；若同一角色仍有直接授权，可以继续出现。 |
| 属性值 true/false/null | Broker 如展示该字段，分别保留“是/否/未知”；授权来源和默认角色选择不由该字段推断。 |
| 中途分页失败或超限 | 明确报告失败，不将部分列表当全部，不静默切换 false，也不把超限解释为无授权。 |
| 服务端/旧 Broker 不支持或能力未确认 | 常规接入继续并如实说明能力边界；模板角色专项验收暂停并提示配套升级。登录刷新、登出不受影响；不能以空列表或部分成功宣称模板验收通过。 |
| 凭证换发 | 生成 profile 后按 SKILL A7 执行各 CLI 的只读身份验证；发现成功与换发成功分别记录。 |

修改 Skill 文档只完成编排契约，不能替代上述 Broker/服务端联调。交付时分别报告本地文档校验与实际联调结果，未执行项明确标注。

## 预发环境联调

先执行 `<bin> show instance --instance <实例域名>`，核对 instance_id、issuer 和 DeveloperAPI 端点与目标环境一致，再运行 `show roles` / `onboard`。CLI 根据实例发现接口选择端点，不臆造 `--pre`、`--endpoint` 参数或手工替换认证域名。端点与预期不一致时停止本次环境验证并交由维护方排查。

首次联调可用 `<bin> onboard --instance <实例域名> --target none --config <独立测试配置文件>`，验证角色发现及 profile 生成，不覆盖日常云 CLI 配置。随后按用户选择的目标 CLI 正式接入并执行 A7 身份验证。

新版 `show roles --json` 保留顶层 `entities`，输出全部页聚合结果；`totalCount` 为本次实际汇总条数，不带未消费的 `nextToken`。它不是服务端单页响应原样透传，不将单页 `maxResults` 套到聚合结果。`TEMPLATE-CREATED` / `template-created` 的 yes/no/unknown 分别展示为“模板创建：是/否/未知”。
